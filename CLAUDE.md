# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project

bloobitygook is an SVG + vanilla JS game engine and the games built on it — a pnpm workspace of small, mostly-pure packages plus one app per game. **The actual product is the tool, not any single game**: a shared ECS core, a growing set of game-logic packages (grid collision, triggers, animation, behavior), an in-browser editor with a GitHub-PR-based game-creation wizard, and a public hub listing whatever's published. See [docs/games-roadmap.md](docs/games-roadmap.md) for the full plan, phase-by-phase history, and what's still ahead (a platformer, as a generic capability demo rather than a specific-IP clone). See [docs/function-dependency-map.html](docs/function-dependency-map.html) (open directly in a browser, no dev server needed) for a collapsible, per-game diagram of what each app's primary loop calls into and which package owns each function.

**Guiding principle carried through every phase**: grow the engine only as far as the next game actually needs. Don't generalize a system until a second real use case demands it — see `packages/triggers` below for the clearest example of this working out. **This principle is superseded by the standing rule immediately below wherever the two conflict.**

## Standing rule: no hardcoded game logic

Effective now, for every package and app in this repo, on every task: **no game-specific logic or content lives as a literal, inline constant or branch in source.** This is a standing command, not scoped to any one task or file — apply it in everything, including code nobody asked you to touch this session, and including existing code as it's next touched.

- **What counts as a violation**: a hardcoded data table (piece shapes, a maze layout, palettes, tuning/scoring constants baked into the function that uses them), and hardcoded control flow (a function that special-cases behavior via an inline string/id check instead of dispatching through a registry).
- **What to do instead**: express it as external, pluggable configuration — data that lives outside the function consuming it, selected/dispatched through a name-keyed registry (the `{name: value}` pattern this codebase already established: `collisionStrategies`, `PICK_STRATEGIES`, `packages/objects`' catalog/definition system). A new variant should be a new config entry or registry registration, never a source edit to existing logic.
- **This overrides the growth principle above, specifically on this dimension**: build the plug point up front for new work, even with only one current consumer — don't wait for a second real use case to justify it, the way the rest of this file otherwise advises.
- **Retroactive**: applies to already-existing hardcoded logic too. A full-repo audit + conversion pass already ran once (Tetris's piece table, Pac-Man's maze/ghost-AI/tuning, the wizard's game-type dispatch and generated-app config, `packages/objects`' definition registry, and `scripts/compose-site.mjs`'s route table — see each area's own section below for the resulting shape). Anything found *after* that pass is still a violation and should be converted the same way, flagging it as you find it rather than doing a silent rewrite.

## Running it

```bash
pnpm install
pnpm dev:play      # http://localhost:5175 — the original blob-physics demo
pnpm dev:editor    # http://localhost:5176 — the dev tool
pnpm dev:tetris    # http://localhost:5178
pnpm dev:hub       # http://localhost:5179 — public games list
pnpm dev:pacman    # http://localhost:5182
pnpm test          # runs every workspace package's test suite
pnpm build         # builds every app, then composes them into dist-site/
```

Needs a real Vite dev server (not `file://`) — ES module imports and scene/manifest fetches both require an HTTP origin. No Turborepo — small enough that plain `pnpm -r`/`pnpm --filter` scripts are simpler; revisit only if build times become annoying.

`functions/` (the Cloud Function in Deployment below) is outside the pnpm workspace, so `pnpm test`/`pnpm build` don't touch it — run `npm test` from inside `functions/` directly.

## Package/app shape

```
packages/
  engine/         pure ECS core + the original ball-physics demo's systems
  grid/           tile-based collision + composite pieces + generic spawner/gravity — built for, and only used by, Tetris-shaped games
  triggers/       generic condition -> action, zero dependencies
  animation/      frame-based sprite animation (SVG attribute swaps, not image assets)
  behavior/       generic state machine + seek/flee movement primitives
  stage/          tiny, dependency-free orchestration (runStage/dispatch) composing whichever systems a game's stage actually needs
  tetris-pieces/  the one genuinely Tetris-specific package — pure piece shape/color/rotation data, no game-rule logic
  game-manifest/  shape/helpers for a published game's games/<id>/manifest.json

apps/
  play/     the blob-physics demo, light + public — deploys to /blob/
  tetris/   a Tetris "stage assembly" wiring packages/grid + triggers + stage + tetris-pieces into one configured instance — /tetris/
  pacman/   full game, on packages/animation + packages/triggers + packages/behavior — /pacman/
  hub/      public list of published games, fetches a Storage-hosted aggregate, no SDK — / (site root)
  editor/   the dev tool — React UI chrome around an imperative engine bridge

functions/  one Storage-triggered Cloud Function maintaining that hub aggregate — outside the pnpm workspace
```

Every game app builds with its own Vite `base` (`/tetris/`, `/pacman/`, `/blob/`) and gets combined into one deployable tree by `scripts/compose-site.mjs` (see Deployment below). `apps/editor` is not part of that composed site — it deploys to its own separate Firebase Hosting site, since it's a dev tool, not something players load.

## Entity/component pattern

Entities are plain objects (`{id, ...fields}`), components are just fields on them, systems are plain functions that `query(world, [...fields])` and mutate matches — no framework, no inheritance. Established in `packages/engine/src/world.js`, reused by every package and app since.

## packages/engine

The original core, still exactly what `apps/play` and the blob-editing half of `apps/editor` run on — and, since the character system (see `packages/objects`/`packages/platformer` below), `apps/goop` too. **Not used by Tetris or Pac-Man's gameplay** — they only pull `createWorld`/`spawn`/`destroy`/`query`/`createSvgElement`/`setAttrs`/`clearChildren`/`startLoop` from it, not the physics systems below. Since Phase 7 of the games roadmap, that split is an enforced package contract, not just convention: `package.json` has two subpath exports, no bare `"."` — `"./core"` (world/svg/loop) and `"./physics"` (everything blob-specific). Tetris/Pac-Man and every game-logic package (`grid`/`animation`/`behavior`) import only `@bloobitygook/engine/core`; `apps/play`, `apps/editor/src/engine.js`, and `apps/goop` import both subpaths as needed.

- `core.js` — re-exports `world.js`/`svg.js`/`loop.js`/`hierarchy.js`, the `"./core"` subpath's entire surface.
- `world.js` — `createWorld`, `spawn`, `destroy`, `query`, `clear`.
- `hierarchy.js` — a generic ECS parent-child relationship, added for the stage-building phase: `attachChild(child, parent, offset)` stamps `child.parentId`/`child.offset`; `hierarchySystem(world)` copies `parent.x/y + offset` onto every child, called from each app's `render()` (not `update()`) so a child visibly tracks its parent even while a scene is frozen for editing, and needs no `dt`. `destroyWithChildren(world, id)` recursively destroys a subtree, children first, via the untouched plain `destroy` — most callers still want simple, non-cascading removal, so that stays the default. An orphaned child (parent destroyed via plain `destroy`) just freezes at its last position rather than crashing — nobody's needed cleanup beyond that yet. `hierarchySystem` is wired into both `apps/editor/src/engine.js`'s and `apps/scene-player`'s render loops unconditionally (a no-op when nothing has a parent), but nothing yet calls `attachChild` outside its own unit test — no scene has an authored parent-child relationship, and no UI exists to create one (see Known gaps).
- `svg.js` — `createSvgElement`, `setAttrs`, `clearChildren`; the only place that touches `document.createElementNS`.
- `loop.js` — `requestAnimationFrame` loop; dt is clamped so a dropped/backgrounded frame doesn't teleport entities.
- `physics.js` — the `"./physics"` subpath's barrel: re-exports `systems.js`'s 6 systems plus `scene.js`/`fileio.js`/`objects/ball.js`/`color.js`. Deliberately does not re-export core, keeping the two subpaths' scope disjoint.
- `systems.js` (formerly `physics.js` before the Phase 7 rename) — continuous bounce physics: `gravitySystem` (`gravity = {mode: "uniform"|"point", magnitude, x, y}`; point mode pulls toward `(x,y)` at *constant* magnitude, deliberately not inverse-square, so one slider is comparable across modes), `integrateSystem` (semi-implicit Euler), `collisionSystem` (floor/wall bounds, restitution/friction — friction is scaled by how hard the contact was (reusing `applyImpact`'s `IMPACT_REFERENCE_SPEED` normalization via `frictionFactor`), not applied at full strength on every contact: a resting body re-enters this branch on essentially every tick as gravity nudges it back below the bound and this function corrects it right back out, and applying full friction on every one of those micro-contacts used to decay a held movement key's velocity to ~0 within a handful of frames regardless of how long the key stayed down; also stamps `entity.grounded = true` on any tick it resolves floor contact, `false` otherwise — a generic physical fact, inert for any entity that doesn't read it, added so `packages/platformer`'s jump logic has something to gate on without duplicating the floor-contact check itself), `ballCollisionSystem` (ball-vs-ball, broad-phased with a uniform grid so it's not O(n²)), `deformationSystem` (a spring driving squash-on-impact), `renderSystem` (the only system touching the DOM).
- `color.js` — `hslToHex`/`randomBallColor`.
- `scene.js` — `serializeScene`/`loadScene` for the blob demo's scene format. `SPAWNERS` maps a scene object's `type` to its spawn function. Gravity is normalized on load so scenes saved before point-gravity existed still load.
- `fileio.js` — File System Access API wrapped with a download-link fallback; `hasFileSystemAccess` guards against `window` not existing at all (Node/test/future-server contexts), not just against the API being unsupported.
- `objects/ball.js` — the blob demo's one entity type.

Package resolution note, relevant to every package here: they all ship raw ESM with no build step. Every other package still exports a single `"."` (`"exports": {".": "./src/index.js"}`) — `packages/engine` is the one exception, with the two subpaths above instead. Every app's `vite.config.js` excludes its workspace deps from `optimizeDeps` by package name (not by subpath, which Vite doesn't distinguish here) — otherwise esbuild's pre-bundler treats a workspace-linked package as an immutable third-party dep and stale-caches it, breaking hot reload on edits.

## packages/grid (Tetris-shaped games)

`collision.js` — `canPlace(occupied, cells, bounds)`, `checkCompleteRows(occupied, bounds)`, `rowAfterClear`/`occupiedAfterClear` (post-clear row-shift math, rebuilt as a fresh `Set` each time rather than mutated cell-by-cell — see its doc comment for the real ordering bug that pattern caused), all pure functions over a `Set` of `"col,row"` keys, no ECS dependency. Also exports `collisionStrategies` — a `{ boundsAndOccupancy: canPlace }` registry so a caller can select a collision strategy by name, with room to add a second implementation later without changing any caller's contract. `cellGroup.js` — the falling composite piece: **one** entity holding a list of relative cell offsets, rendered as one `<g>` with N `<rect>` children that get reused (not recreated) across rotations. `block.js` — the individual static cells a piece decomposes into on landing, which is what line-clearing actually needs to query/remove one at a time.

Three more generic capabilities, added when Tetris was rewritten to pull reusable tools out of what used to be Tetris-owned logic, rather than a Tetris-specific package:
- `transform.js` — `attemptTransform(piece, patch, occupied, bounds, strategy = canPlace)`, the one shared "try a candidate change, roll back on collision" helper. Used identically for horizontal moves, rotation, and drop ticks, so none of them hand-duplicate "build a candidate, test collision, mutate-or-reject."
- `spawner.js` — `createSpawner({candidates, strategy})`, generic candidate selection with lookahead (`next()`/`peek()`) — nothing here knows "piece" is a Tetris concept; a future game could spawn enemies/items through the same function. Each strategy is a factory returning a stateful `pick()` closure, so a future stateful strategy (e.g. a shuffled-bag algorithm) is a new registry entry, not a redesign.
- `gridGravity.js` — `applyGridGravity(entity, direction, occupied, bounds, strategy)`, the discrete, direction-configurable counterpart to `packages/engine`'s continuous physics `gravitySystem` (not a unification of the two — continuous-velocity integration and discrete per-tick stepping are different computations). `direction` is a `{dcol, drow}` vector; `{dcol:0, drow:1}` is "down" for Tetris, but nothing here assumes that.

Deliberately no true parent-child ECS relationship, no formal game-config package inside grid itself — that composition role belongs to `packages/stage` instead (below). Tetris's board is procedural (nothing authored to save); its moves are just validated-mutation calls, now made via the generic `attemptTransform`/`applyGridGravity` rather than app-owned duplicated logic.

## packages/triggers

`createTrigger({condition, action})` + `runTriggers(world, triggers)` — condition returns whatever matched, action runs once per tick something did, `runTriggers` returns which triggers fired and their matches (so a caller like Tetris's scoring doesn't need to re-derive what happened). Zero dependencies. `zone.js` adds a spatial-entry helper (`createZone`/`isInsideZone`/`zoneEntryCondition`) for portal-style triggers.

This is the one package whose generalization got real validation, not just a plausible-sounding unit test: Tetris's line-clearing was retrofitted from an inline `checkCompleteRows`+`clearRows` call to a `lineClearTrigger`, confirmed byte-identical before/after. Pac-Man's tunnel portals are the second use case, and a genuinely different shape (spatial zone entry vs. a board-state condition) — good evidence the abstraction actually covers more than one thing.

`tieredGoal.js` — `createTieredGoalTrigger({condition, tierNames, onAchieve})`, built on top of `createTrigger` (unchanged). Generalizes "count how many things completed at once, name the tier" — Tetris's single/double/triple/tetris line-clear naming is the validating second use case for this specific pattern, the same way portals validated the base condition→action shape.

## packages/animation

`createAnimation(frames, fps)` + `advanceAnimation` (pure step function, separated from the ECS loop for testability, uses a `while` loop so a large `dt` catches up to the correct frame instead of falling one behind) + `animationSystem(world, dt)`. A "frame" is a set of SVG attributes to apply, not an image asset — consistent with how the rest of the engine renders. Used by Pac-Man for a chomp pulse (a radius swap, not literal mouth-shape path-arc math — proves the mechanism without geometry work that's polish, not capability).

## packages/behavior

`createBehavior(states, initial)` + `stepBehavior` + `behaviorSystem(world, dt)` — a generic state machine; each state has an optional `update(entity, dt, world)` and `next(entity, world)` returning the state to transition to. Deliberately has no "ghost" concept baked in. Also exports `seekToward`/`fleeFrom`, pure continuous-position movement primitives.

**Only the state-machine half has a real consumer.** Pac-Man's ghosts use `createBehavior`/`behaviorSystem` for their chase/flee states, but ghost *movement* goes through `apps/pacman`'s own tile-locked `movement.js` + `ghostAI.js` (intersection direction-choice by closest/farthest targeting), not `seekToward`/`fleeFrom` — those remain unit-tested only, not yet proven against a real app. Worth remembering before assuming they're validated the way the state machine is.

`presets.js` — `BEHAVIOR_PRESETS = {stationary, patrol, patrolKinematic, chase}`, a name-keyed registry (a new preset is a new entry, not a redesign) an archetype's `{mode:"scripted"}` behavior picks from instead of a hand-authored `states` config (see `packages/objects`' `archetype.js`). `patrol`/`chase` steer via `vx` rather than `seekToward`'s direct position-set — archetype-spawned entities are continuous-physics bodies where `vy` is owned by gravity/collision, not behavior, so only steering horizontal velocity stays compatible with `packages/engine`'s systems instead of fighting them every tick. `patrol` records its origin lazily on an entity field the first time it runs (a preset has no visibility into where a given instance was placed); `chase` finds its target via the `player: true` tag convention (`query(world, ["player"])[0]`), sitting still if none exists yet. Live-verified in `apps/goop`, not just unit-tested — a real state transition (patrol reaching its boundary and reversing `vx`) confirmed against the actual running physics loop. `patrolKinematic` is `patrol`'s counterpart for a non-dynamic entity (a moving platform, `physics.dynamic:false` — see `packages/objects`' `archetype.js`): since `integrateSystem` never applies `vx` to a non-dynamic entity, this preset mutates `entity.x` directly instead — `behaviorSystem` queries only `["behavior"]`, so it runs regardless of `dynamic`. Kept as a separate preset (not a branch inside `patrol`) so a dynamic entity's behavior stays exactly what it was.

## packages/stage

`runStage(stage, world, dt)` + `createActionDispatcher(stage)` — genuinely generic, zero dependencies (not even on `engine`/`grid`/`triggers`), because it only composes whatever functions a `stage` config hands it rather than assuming any particular game shape. `runStage` calls each `{fn, config}` in `stage.systems` as `fn(world, dt, config)` every tick (matching `packages/engine`'s own established system-function convention) — a stage only lists the systems it actually needs. `createActionDispatcher` is the event-driven counterpart: `dispatch(action, ...args)` looks up `stage.controls[action]` and calls it, for input-triggered moves (move/rotate/hard-drop) as opposed to `runStage`'s continuous per-tick systems (gravity). Built when Tetris was rewritten, but nothing here is Tetris-specific — a stage is just whichever systems/controls its assembly code chooses to wire in.

## packages/tetris-pieces

The one genuinely Tetris-specific package, and it's pure data: `PIECES` (the 4-precomputed-rotation-states-per-piece table, ported from the Python prototype — see `apps/tetris` below) and `PIECE_COLORS` live in `pieces.json`, not as source constants — `pieces.js` just imports and re-exports them (plus `PIECE_TYPES`, `cellsForRotation`, `spawnPiece`), so swapping or extending the piece set is a data-file edit, not a source edit (per the standing no-hardcoded-logic rule). No collision, no spawning logic, no game rules — just what a tetromino *is*. Everything that used to be piece-selection logic (`randomPieceType`) moved into `packages/grid`'s generic `spawner.js` instead, since choosing among candidates isn't a Tetris-specific concept.

## packages/game-manifest

`createManifestEntry`/`isValidManifestEntry` — the shape of a `games/<id>/manifest.json` entry (`id`, `title`, `description`, `route`, `thumbnail`, `published`, `createdAt`, `sceneId`), pure, no Firebase dependency. Used by `apps/hub` (reading) and `apps/editor`'s `games.js` (writing) so neither pulls in the other's I/O concerns. `sceneId` (string or `null`) is which `scenes/<id>.json` a game's canvas editor loads — `null` for games with no editable scene yet (every hand-coded game, e.g. Tetris/Pac-Man; only the blob demo has one).

## packages/svg-import

`sanitizeSvg(rawSvgString) -> cleanSvgString`, the one place this repo accepts untrusted markup from a file the user picked (an archetype's imported SVG visual — see `packages/objects`' `archetype.js` below). Wraps `dompurify` (a proven, maintained sanitizer, not hand-rolled regex stripping) with an SVG-only profile plus two extra `FORBID`s a bare profile leaves open: `style` (CSS `url()` exfiltration) and `use`/`image` (external-reference indirection). Always deals in fragments (no `<svg>` wrapper) as both input and output — a bare shape fragment has to be wrapped before handing it to DOMPurify (without `<svg>` context the HTML parser doesn't recognize SVG-only elements as foreign content and silently drops them), and the wrapper is stripped back off the result so callers always get a fragment back. Callers sanitize twice — at import time (before persisting an archetype) and again at spawn time (defense in depth, since a stored string should never be trusted as pre-clean).

## packages/objects

The generic object-catalog layer sitting above `engine`/`grid`/`tetris-pieces`, built so the editor's scene canvas isn't hardcoded to one entity type (a physics ball) anymore. An **object definition** is a plain object — `{id, category, label, swatch, coordinateSpace, cellSize?, spawn(world, worldEl, def), serialize(entity), buildSpawnDef(x, y, catalog)}` — matching the codebase's existing `{name: value}` registry precedent (`collisionStrategies`, `PICK_STRATEGIES`) rather than a class hierarchy. `createCatalog(definitions)` (`catalog.js`) gives `byId`/`all`/`byCategory`/`enabledIn(ids)` — `enabledIn` is what lets one game declare "which of these I actually use" (its `catalogIds`), returning a same-shaped, composable, narrowed catalog.

Every spawned entity gets stamped with `entity.catalogId` at spawn time (`instantiate.js`'s `instantiateObject`/`serializeObject`) rather than being identified back by `entityType` — necessary because all 7 Tetris piece definitions spawn a `"cellGroup"` entity (per `packages/grid`), so `entityType` alone can't disambiguate which piece type an entity is on save.

`standard.js` assembles `STANDARD_DEFINITIONS`/`STANDARD_CATALOG` by discovering every module under `definitions/*.js` via `import.meta.glob` (each one's default export is a definition or an array of them) rather than a hand-maintained import list — adding a new definition file needs zero edits to `standard.js`, matching `apps/play/src/scenes.js`'s "drop a file in" pattern. Today that's: `ball` (wraps `packages/engine`'s `spawnBall`, paired with a `serializeBall` that now lives next to it in `objects/ball.js`), the 7 Tetris piece types (`definitions/pieces.js`, wrapping `tetris-pieces`' `spawnPiece`; `coordinateSpace: "grid"` quantizes an editor click to `col`/`row` — purely for authoring on the fixed pixel canvas, no bearing on a game's real board size), a `"spawner"` tool (`definitions/spawner.js`, category `"tool"`) — a placeable marker holding config (category + allowed-types subset + a `packages/grid` `SPAWNER_STRATEGIES` name) for a future gameplay pass to read and drive real spawning from; nothing consumes it yet, this pass only lets it be placed and edited — and `"blob"` (`definitions/character.js`, category `"character"`) — see below.

**`definitions/character.js`** — the first `"character"`-category definition, built for `apps/goop`. `spawnCharacter` builds the same physics-entity field set `spawnBall` does (this package depends on `@bloobitygook/engine` already; adding a character concept there would contradict `objects/ball.js`'s "the blob demo's one entity type" scoping, so it lives here instead, not in `packages/engine`) — deliberately *not* by calling `spawnBall` itself, since that hardcodes `entityType: "ball"`. Two fields a ball doesn't have: `animations` (a name-keyed map — `{idle: {frames, fps}}` today, even with one entry, so a second named animation like `walk`/`jump` is a data addition later, not a shape migration; `entity.animation` itself is the *live* `createAnimation(...)` instance `packages/animation`'s `animationSystem` expects, so the active name is tracked separately as `entity.animationName`) and `stats` (an open bag — `moveSpeed`, `jumpImpulse`, `health`, whatever a game needs, arbitrary and unschema'd, per the standing no-hardcoded-logic rule: a new stat is config, not a code change). `entity.el` and `entity.circleEl` are the *same* `<circle>` node, not a circle wrapped in a group like a plain visual hierarchy might suggest — `renderSystem`'s transform and `animationSystem`'s frame-attribute swaps both always target `entity.el`, so a separate wrapper would put the two systems' writes on different elements and animation would silently do nothing.

`scene.js` (not `packages/engine`'s, which now only keeps gravity normalization — `packages/engine` can't depend on this package, since this package depends on it) generalizes `loadScene`/`serializeScene` to take a `catalog` argument, looking up spawn/serialize per entry instead of a hardcoded `SPAWNERS` map. `catalogIdsOf(sceneData)` defaults to `["ball"]` when a scene file predates this system, so every previously-saved scene (`apps/editor/public/scenes/default.json` included) still loads byte-identically. `serializeScene` also takes an optional `nextSceneId` (defaulting to `null`), and `nextSceneIdOf(sceneData)` reads it back — the stage-building phase's scene-navigation mechanism: a game's scene sequence is a simple linked chain (this scene's own `nextSceneId` points at the next one), not a manifest-level list or a branching graph, deliberately scoped that way to avoid touching `packages/game-manifest`'s widely-depended-on shape. `apps/scene-player` follows it on reaching a goal; `apps/editor`'s `ScenePanel` is the authoring side (see below).

`sceneLoader.js` — `loadSceneWithArchetypes({sceneData, world, worldEl, fetchArchetype})`, the shared "load a scene file into a live world, resolving any archetype ids the built-in `STANDARD_CATALOG` doesn't know" path both `apps/editor`'s `engine.js` and `apps/scene-player` now call, replacing what used to be `engine.js`-only inline fetch/resolve logic. `fetchArchetype` is **injected**, not imported — keeps this package Firebase-free, the same pattern `packages/triggers/zone.js` already uses for `entityFilter`. Walks an id's `extends` ancestors transitively (not just the scene's own listed `catalogIds`) before resolving inheritance and building definitions, so an archetype can extend a base the scene never mentions directly. A missing/offline archetype is simply left out, matching `loadScene`'s own "unknown type — skipped" tolerance, rather than failing the whole load.

**`archetype.js`** — the no-code layer: a user-authored **archetype** (created/edited entirely in `apps/editor`'s Archetypes UI, no code file) is a plain JSON record — `{id, label, category, swatch, boundingRadius, extends?, physics:{restitution,friction,dynamic?,platformSize?}, properties:[{name,default,required}], visual, behavior}` — interpreted by one generic `spawnFromArchetype`/`serializeFromArchetype` pair rather than a bespoke spawn function per type.

`extends: <archetypeId>` is archetype **inheritance**, resolved by `resolveArchetype(archetype, byId)` — walks the chain, merging parent → child (`physics`/`visual` shallow-merge with the child winning; `properties` concatenate with same-named entries overridden; `behavior` is replaced wholesale by whichever is more specific — merging two different behavior shapes field-by-field wouldn't make sense). A visited-id guard throws a clear error on a cycle instead of recursing forever. `spawnFromArchetype`/`archetypeToDefinition` never need to know inheritance exists — resolution always happens first, in the shared loader (`sceneLoader.js`, below). The stage-building phase's moving-platform archetype is the validating second use case (extends a static-platform base, overriding only `behavior`).

`physics.dynamic` (optional, defaults `true`) and `physics.platformSize:{width,height}` (optional) are the stage-building phase's platform mechanism: a platform archetype sets `dynamic:false` so it neither falls nor bounces off stage bounds, moving only via its own behavior (`patrolKinematic`, see `packages/behavior`). Critically, `spawnFromArchetype` **omits** the `dynamic` field entirely rather than setting it `false` — `packages/engine`'s `query()` matches on field *presence*, not truthiness, so a lingering `dynamic: false` key would still be picked up by `gravitySystem`/`integrateSystem`/`collisionSystem`/`ballCollisionSystem`. `platformSize`, when set, is read by `packages/platformer`'s `platformCarrySystem` and also reshapes a `rect` shape-visual to that footprint instead of the usual `boundingRadius`-sized square (see the `visual` paragraph below) — a platform's actual look, not just its carry logic. `archetypeToDefinition(archetype)` wraps a record into an ordinary catalog definition, so `createCatalog`/`instantiateObject`/`serializeObject`/`scene.js` need zero changes to support it — they already treat a definition as an opaque bag. `properties` becomes `entity.stats` at spawn (formalizing `character.js`'s stats-bag idea with defaults/required metadata); a missing **required** property falls back to its own default rather than throwing, so a stale/hand-edited record can never crash a scene load (`required` is enforced by the editor form when saving, not here). Every archetype-spawned entity shares `entityType: "archetypeInstance"` (like all 7 Tetris pieces sharing `"cellGroup"`) — `catalogId` disambiguates, as usual.

`visual` is a tagged union: `{kind:"shape", shape:"circle"|"rect", fill}` uses the same bare-element trick as `character.js` (`el === circleEl`, full animation support) — a `rect` normally draws a `boundingRadius`-sized square (collision stays circular regardless of visual, per below), except when the archetype also sets `physics.platformSize`, in which case the rect visual matches that width/height instead, since a platform's footprint is genuinely rectangular, not square; `{kind:"svg", svgMarkup}` spawns a `<g>` wrapper with the sanitized (via `packages/svg-import`, re-sanitized here too — defense in depth) markup as its content — `renderSystem`'s transform already just targets `entity.el` regardless of tag, so this needed no engine change, but **animation is unsupported for this visual kind** (a single frame's attribute-set has no one element to apply to once the visual is several child shapes) — the archetype editor hides animation fields when visual kind is `svg`, a stated scope line, not a silent gap. Collision always stays circular via `boundingRadius`, decoupled from the visual — no polygon collision, even for an SVG shape.

`behavior` picks one of three modes, wired up by `attachBehavior` at spawn time: `{mode:"static"}` attaches nothing; `{mode:"scripted", preset, ...config}` looks up a name from `packages/behavior`'s `BEHAVIOR_PRESETS` and wires a real state machine into `entity.behavior`; `{mode:"input", inputMap}` stamps `entity.player = true` (the same tag idiom as `apps/pacman`'s `movable: true`, letting a "chase" preset find the player generically) and stores the key map on **`entity.inputMap`, deliberately not `entity.behavior`** — `behaviorSystem` queries every entity with a `behavior` field and assumes a real `{states,current}` machine, so an input-mode entity's key map living there would crash it the first tick it ran.

## packages/platformer

Continuous-physics platformer movement, layered on top of `packages/engine`'s existing gravity/collision rather than a new kinematic character-controller — a deliberate pivot from what `docs/games-roadmap.md`'s original platformer plan assumed (see that doc's own note). Zero dependencies, mirroring `packages/triggers`' shape. `applyMoveInput(entity, direction, moveSpeed)` sets `vx` directly from a held `-1|0|1` direction; `applyJump(entity, jumpImpulse)` only applies (sets `vy = -jumpImpulse`, clears `entity.grounded`) when `entity.grounded` is true (set by `packages/engine`'s `collisionSystem`), returning whether it actually jumped. Moving platforms landed in the stage-building phase (`platformCarry.js`, below); ladders and one-way platforms are still deliberately out of scope.

`actions.js` — `ARCHETYPE_ACTIONS = {moveLeft, moveRight, stopMoving, jump}`, a name-keyed registry (not a switch) wrapping `applyMoveInput`/`applyJump`, reading tunables from `entity.stats` — what an archetype's `{mode:"input"}` `inputMap` names by string. `keyboardController.js` — `createKeyboardController(entity, actions = ARCHETYPE_ACTIONS)` → `{handleKeyDown(key), handleKeyUp(key)}`, reading `entity.inputMap[key].onPress/onRelease` — generalizes what `apps/goop` used to hand-wire per-app (a `held` Set + manual left/right reconciliation) into something data-driven. Two opposing keys held at once (e.g. both arrows) reconcile without any hardcoded notion of "direction": releasing one replays every still-held key's `onPress` in press order, so the most-recently-pressed one naturally wins on an overwrite-style action like `applyMoveInput` — no special-casing which action names are "opposite" each other.

`platformCarry.js` — `platformCarrySystem(world)`, the stage-building phase's moving-platform mechanic: queries entities with `platformSize:{width,height}` (a rect footprint, set by a platform archetype's `physics.platformSize` — see `packages/objects`' `archetype.js`) against every circle-radius entity, and if one is standing on top (horizontal overlap + feet within a few px of the platform's top edge), carries it by that frame's platform position delta (tracked via lazily-initialized `prevX`/`prevY`, the same idiom `patrol` already uses for its origin) and restamps `rider.grounded = true`. Deliberately scoped to exactly this case, not a general rect-vs-circle collision system — everything else in `packages/engine` is circle-vs-circle/circle-vs-bounds, and generalizing that would be a real physics-model change affecting every existing consumer (the blob demo included). A future "pushed sideways" or "standing on a slope" need would require a real rect-collision pass, not an extension of this function.

## apps/goop

The end-to-end proof of the archetype system — every entity is spawned from a plain data record (`src/config.json`'s `archetypes` array), not a hand-written spawn function, via `createCatalog(config.archetypes.map(archetypeToDefinition))` + `instantiateObject`: a `"goblin"` (`{mode:"input"}`, keyboard-controlled via `packages/platformer`'s `createKeyboardController`) and a `"patroller"` (`{mode:"scripted", preset:"patrol"}`, driven by `behaviorSystem`). Not part of the composed site (no `bloobitygook.route` in its `package.json`) — a capability proof, not a published game.

## apps/scene-player

The stage-building phase's playable runtime — loads **any** published scene (`?scene=<id>` in the URL) and runs the full tick loop (physics + behavior + a goal trigger), rather than the editor's frozen Setup canvas or `apps/goop`'s hardcoded `config.json`. Reads `packages/objects`' `loadSceneWithArchetypes` for loading, so it gets archetype-inheritance resolution for free. **Zero Firebase SDK dependency**, mirroring `apps/hub/src/games-storage.js`'s plain-`fetch`-against-the-public-download-URL pattern exactly (`src/scene-storage.js`) rather than pulling in a Storage client — keeps this gameplay app as dependency-light as `play`/`tetris`/`pacman`/`goop`. `fetchScene`/`fetchArchetype` try the cloud path first, falling back to a local file under `public/scenes/`/`public/archetypes/` (the same fallback shape `apps/editor`'s `engine.js` already uses for `loadSceneData`) — this app is usable, and its own proof-slice content ships, without cloud credentials.

`src/main.js`'s tick order — `gravity → behaviorSystem → integrate → collision → platformCarrySystem → ballCollision → deformation → animation → runTriggers`, then `render()` running `hierarchySystem` before `renderSystem` — matches `apps/editor/src/engine.js`'s Run-mode loop exactly, so a scene behaves identically whether it's being tested in the editor or actually played. Any placed entity whose definition's `category` is `"goal"` (a well-known category name, same idea as the spawner tool's `"tool"`) becomes a `packages/triggers` zone-entry trigger built from its position + `stats.width/height` — the first real "reaching a goal" use case for that package, validating it the same way Tetris's line-clear and Pac-Man's portals did earlier. On entry: if the just-finished scene has a `nextSceneId`, this app re-fetches and loads that scene (updating the `?scene=` query param via `history.replaceState` so reload/sharing still points at the right level); if not, it shows a terminal "You win!" status — a valid, expected end, not an error. `public/scenes/platformer-1.json` → `platformer-2.json` is the proof-slice two-scene chain, using three plain, no-code archetypes (`public/archetypes/hero.json`, `platform.json`/`moving-platform.json` — the latter `extends` the former, the inheritance system's second validating use case alongside the base — and `goal.json`), not new code-shipped definitions.

## apps/tetris

`src/main.js` is a Tetris **stage assembly**, not owned game-rule logic — every rule it applies (collision, spawning, gravity, tiered goal detection, transform-attempt-and-reject) is a generic capability imported from `packages/grid`/`triggers`/`stage`; board size, spawn origin, drop direction, piece set, and scoring all live in `src/config.json`, imported by `main.js` rather than declared as constants there — hand-editable without touching this file's logic. The piece rotation table itself lives in `packages/tetris-pieces` (ported from the original Python prototype `valkirie/tetris/pieces.py` — same 4-precomputed-rotation-states-per-piece idea, translated from pixel `Vector` offsets to grid `{col,row}` offsets; verified structurally there, not here).

Features: hard drop (`space` — loops `applyGridGravity` until blocked, no new primitive needed), a next-piece preview (powered by the spawner's `peek()`), and a level system (drop speed increases and score multiplies as `totalLinesCleared` crosses `linesPerLevel` thresholds — this state is app-level, not a generic capability, since it's specific to how *this* game paces and scores itself). Line-clear scoring is tiered (single/double/triple/tetris) via `packages/triggers`' `createTieredGoalTrigger`.

**Known, accepted tradeoff**: `apps/editor/src/scaffold/tetris-template.js`'s wizard-generated Tetris instances mirror this file's assembly shape as a hand-maintained generated-code template, not a shared runtime function call — consistent with how the wizard already bakes app-identity values (port/id) as literal generated code, not a new problem introduced here. Board/scoring/pacing values themselves are NOT part of that tradeoff — the wizard generates a `config.json` for the new app too (same shape as this one), rather than baking those values into the generated `main.js`. Keep the two `main.js`/`config.json` pairs in sync by hand when either's logic (not just its config) changes.

## apps/pacman

**Does not depend on `packages/grid`** — Pac-Man needs continuous tile-locked movement (smooth between cell centers, not instant jumps), a different enough shape from Tetris's discrete drops that it got its own `movement.js` instead.

- `maze.js` — mazes are discovered from `../mazes/*.json` via `import.meta.glob` (mirroring `apps/play/src/scenes.js`'s exact pattern), each `{id, rows, tunnelRow}`; `maze.js` loads the first/default one (today, just `mazes/classic.json`, an 11×9 ASCII layout — `#` wall, `.` pellet, `o` power pellet). `tunnelRow` (the one row `isWallAt` allows a column outside `[0, COLS)` through) comes from the loaded maze's own data, not a hardcoded constant, so a maze with a different tunnel row (or none) needs no code change. Connectivity is checked by an automated flood-fill/BFS test from the player's spawn point, not just a by-hand walkthrough — exactly the kind of thing a hand-authored maze can get subtly wrong (an isolated, uncollectable pellet).
- `movement.js` — `tryMove(entity, dt, isBlocked, cellSize)`, shared by the player and ghosts alike; the only difference between them is *who* sets `queuedDirection` (keyboard vs. `ghostAI.chooseDirection`). **Finds the target cell via direction-aware `floor`/`ceil`, not `Math.round`** — round is ambiguous once an entity is past its current cell's midpoint, which caused a real bug during development (an entity could round back to the cell it just left and oscillate forever instead of progressing; caught by a multi-tick accumulation test, not by playing). Uses a `while` loop so reaching a target with movement budget left over re-decides (turn/continue/stop) immediately, not one frame late — the one-frame-late version let a blocked entity's stale direction briefly poke it into the wall.
- `ghostAI.js` — `chooseDirection(col, row, currentDirection, target, isBlocked, preference)`, picks the best open neighbor by distance to target. Which comparison "closest" (chase)/"farthest" (flee) applies is a `TARGETING_STRATEGIES` name-keyed registry (mirrors `packages/grid`'s `PICK_STRATEGIES`), not an inline branch — throws on an unknown preference. Won't reverse direction unless it's a dead end.
- `main.js` — wires walls/pellets/player/ghosts, portals (two `packages/triggers` zones on the tunnel row's far edges), ghost chase/flee via `packages/behavior`, the chomp pulse via `packages/animation`, scoring, win/lose, restart. Cell size, speeds, spawn points, colors, scoring, and the chomp animation's frame data all live in `src/config.json`, not as constants here. The player/ghost entities are tagged `movable: true` at spawn so the render/portal-trigger systems can `query(world, ["movable", ...])` instead of special-casing `entityType === "player" || entityType === "ghost"` by name.

352×288 board at 32px cells.

## apps/editor

The dev tool. Routed via `react-router`: `/` is a dashboard listing every game, `/:gameId` is a single game's editing view — editing is always scoped to one game at a time, never a free-floating "current scene." UI chrome is React; the physics world, SVG stage pointer handling, and 60fps render loop are not (they don't belong in React's re-render model).

- `src/App.jsx` — `BrowserRouter` > `CloudAuthProvider` > `AppHeader` (sign-in, status, New Game trigger, always mounted regardless of route) + the two routes + `WizardPanel` (a centered overlay reachable from either route).
- `src/routes/Dashboard.jsx` — lists games via `listGamesForEditor`, each linking to `/:gameId`; games are never created here directly, only opened (typing a not-yet-existing id and hitting Open just navigates — `GameEditor` handles the actual first save).
- `src/routes/GameEditor.jsx` — fetches the current game's manifest (its draft copy if one exists and the user can read it, else the public copy, else an empty `{id: gameId}` for a brand-new listing), always renders `GameMetadataForm`, and additionally renders `Stage`+`Toolbar`+`Palette`+`Inspector`+`ScenePanel` only when the manifest has a `sceneId` — most games (Tetris, Pac-Man) don't, so they get metadata-only editing. `GameEditorRoute` wraps it with `key={gameId}` so switching games fully unmounts/remounts the subtree rather than relying on effect-dependency reasoning.
- `src/engine.js` — the imperative bridge for the scene canvas. Owns `world`/`gravity`/`mode`/`catalog`/`armedId`/`selected`/`currentSceneId`/`nextSceneId` as module state, exposes a `useSyncExternalStore`-compatible store (`subscribe`/`getSnapshot`) plus action functions (`setMode`, `setPaletteSelection`, `updateSelectedProp`, `updateSelectedStat`, `handleStagePointerDown`, `switchScene`, `createLinkedScene`, `setCatalogIds`, ...). `catalog` is rebuilt every time a scene loads via `packages/objects`' shared `loadSceneWithArchetypes` (`applyLoadedScene`, shared by `initEngine`/`openSceneFromFile`/`loadSceneFromCloud`/`switchScene`/`setCatalogIds`) since a different file (or a different enabled-id set) can enable a different object set; `armedId` names which catalog entry the next stage click places, defaulting to the catalog's first entry so a ball-only scene keeps the original "click anywhere spawns a ball" UX with zero palette interaction required. `handleStagePointerDown` no longer hardcodes ball-spawning: it hit-tests via `findEntityAt` (generalized from the old `findBallAt`), then defers to the armed definition's own `buildSpawnDef(x, y, catalog)` to build whatever `instantiateObject` needs. `initEngine({..., sceneId})` takes which scene to load (published copy preferred, falling back to a local `public/scenes/<id>.json`, falling back to empty) since `Stage` can mount for a different game each time the route changes — paired with a real `disposeEngine()` (stops the physics loop via `startLoop`'s returned stop-function, resets all module state) called from `Stage`'s unmount effect, replacing what used to be a permanent one-shot `initialized` latch from when there was only ever one `Stage` for the app's whole lifetime. `update()`'s tick order (`gravity → behaviorSystem → integrate → collision → platformCarrySystem → ballCollision → deformation → animation`) and `render()` (`hierarchySystem` then `renderSystem`) match `apps/scene-player`'s runtime loop exactly, so Run mode is a faithful preview of how a scene will actually play. `switchScene(sceneId)` (stage-building phase's scene navigation) re-runs the same `applyLoadedScene` path against a different scene id, replacing the live world in place — no route change, since `sceneId` isn't part of the URL and doesn't need to be bookmarkable. `createLinkedScene(newSceneId)` publishes the current scene (with `nextSceneId` now set) and a fresh empty scene at the new id, then switches to it — the one authoring flow that actually needs scene navigation (building a level sequence one at a time).
- `src/components/Stage.jsx` — renders the `<svg>` shell via JSX, hands `engine.js` refs plus the current `sceneId` in a mount effect, and never re-renders its contents; disposes on unmount.
- `src/components/{Toolbar,Palette,Inspector,ScenePanel}.jsx` — read `engine.js`'s store via `useSyncExternalStore`; `Toolbar` takes `sceneId` as a prop (scene editing/gravity/local save-open only — sign-in, game listing, and the wizard moved out to `AppHeader`/`Dashboard`). `Palette.jsx` is a sibling of Toolbar/Inspector, not nested in either — category-grouped buttons sourced from the snapshot's `catalog`, each arming `setPaletteSelection` for the next stage click; a game with one enabled object (every existing blob-demo scene) renders one button, unchanged from before this existed. `Inspector` branches on `selected.catalogId`/`definitionCategory`/`stats` (independent, non-exclusive `&&` renders, not if/else) — the original ball fields, a spawner-config branch (category/allowed-types/strategy, the last sourced from `packages/objects`' re-exported `SPAWNER_STRATEGIES`), a generic stats branch (one editable number input per `entity.stats` key, keyed on `stats !== undefined` rather than a category string — collision-free with the spawner branch as long as an archetype avoids category `"tool"` specifically, which is what a goal archetype's own category `"goal"` is for), and a minimal label+Delete fallback for anything else (e.g. a placed piece) — no schema-driven form engine, just explicit branches. `ScenePanel.jsx` (stage-building phase) is scene-level, not object-level: an **Objects** section (checkboxes over `STANDARD_DEFINITIONS` + `listArchetypes()`'s ids, toggling `engine.js`'s `catalogIds` — the UI gap this closes was that a scene's enabled-id set used to be scene-JSON-only, with nothing in the editor letting you choose it) and a **Flow** section (current scene id / next scene id, a "Go" button calling `switchScene`, and a "New (linked as next)" button calling `createLinkedScene`).
- `src/components/GameMetadataForm.jsx` — the id/title/description/route/sceneId/published fields for one game; id is read-only (always the route's `gameId`, so renaming means navigating elsewhere, not retyping in place). "Save Draft" and "Publish" are two different actions hitting two different Storage paths (see `games.js` below), gated by two different permission tiers.
- `src/permissions.js` — `canPublish(user)`, a UI-only allowlist check that deliberately duplicates `storage.rules`' `isCanPublish` list by hand (no shared source of truth between client code and Storage rules — a stale client list only produces a confusing disabled button, real enforcement is server-side).
- `src/CloudAuthContext.jsx` — wraps Firebase auth state in a React context via `useEffect`+`useState`.
- `src/firebase-client.js` — the *only* place that calls `initializeApp` (calling it twice throws); `publish.js` and `games.js` both import `auth`/`storage`/`isCloudEnabled` from here rather than each creating their own.
- `src/publish.js` — scene publish/fetch to `scenes/<id>.json` in Storage, gated by sign-in (the `canEdit` tier), separate from local Save/Open (File System Access), which keeps working unauthenticated. No live listener — publishing is explicit and occasional, not sync.
- `src/games.js` — `publishGame`/`fetchGame`/`listGames` target the public `games/<id>/manifest.json` (the `canPublish` tier, per `storage.rules`); `saveDraft`/`fetchDraft` target `drafts/games/<id>/manifest.json` (the `canEdit` tier — editing a draft never makes it visible on `apps/hub`, only publishing does); `listGamesForEditor(user)` merges both for the dashboard, skipping the drafts read entirely when signed out rather than attempting a call `storage.rules` would reject.
- `src/routes/Archetypes.jsx` + `src/components/ArchetypeEditor.jsx` — the no-code archetype UI (see `packages/objects`' `archetype.js`): one route (`/archetypes`, linked from `AppHeader`) lists/creates/edits in place rather than a separate URL per archetype, since the list is expected to stay small. The editor form covers id/label/category/swatch/bounding radius/physics, a "Non-dynamic (a platform)" checkbox that sets `physics.dynamic:false` and reveals width/height fields for `physics.platformSize` (stage-building phase), an add/remove properties table (name/default/required), a visual picker (shape+color, or paste-SVG-markup with a live sanitized preview via `packages/svg-import`'s `sanitizeSvg`), and a behavior-mode selector with three conditional sections (static/scripted-preset — `stationary`/`patrol`/`patrolKinematic`/`chase`, sourced from `packages/behavior`'s registry — /input-keymap) — explicit branches, no schema-driven form engine, matching `Inspector.jsx`'s style. No UI yet for `extends` (archetype inheritance) — the data model and merge algorithm are built and tested, but picking a parent archetype in this form is a fast-follow, not yet wired (see Known gaps). `src/archetype-form-helpers.js` holds the pure bits (`emptyArchetype`, `inputMapToRows`/`rowsToInputMap` — an input map's `{key: {onPress,onRelease}}` shape can't hold an in-progress-editing `""` key or be renamed in place, so the form works in rows and only converts at load/save time — and `hasRequiredPropertyMissingDefault`, which disables Save rather than let a required property with no default reach `spawnFromArchetype`), split out for the same reason `ui-helpers.js` exists: unit-testable without a browser.
- `src/archetypes.js` — `publishArchetype`/`fetchArchetype`/`listArchetypes`, mirroring `publish.js`'s scene functions exactly (`archetypes/<id>.json` in Storage, public read + `canEdit` write, single-tier like scenes — not two-tier like games, since an archetype is a shared building block, not a "publish this game" gate). `fetchArchetype` is the function injected into `packages/objects`' `loadSceneWithArchetypes` (see above) — `engine.js`'s `applyLoadedScene` is `async` because that whole load-and-resolve path is.
- `src/scaffold/{template,tetris-template,repo-edits}.js` + `src/github-wizard.js` — the "New Game" wizard, unrelated to the manifest system above: it scaffolds real app code and opens a GitHub PR (Octokit), it doesn't touch Storage at all. A browser page can't write repo files or push commits directly, so this is the workaround: `template.js` generates the minimal engine-connected app shell (pure); `tetris-template.js` generates a complete, configured Tetris instance instead — board size/cell size/piece subset/drop speed/lines-per-level land in a generated `config.json` (all defaulting to `apps/tetris`'s own `config.json` values — see `## apps/tetris` above), imported by the generated `main.js` rather than baked into it, mirroring `apps/tetris/src/main.js`'s stage-assembly shape as generated code. Which generator a "Game type" selection (`blank`|`tetris`) runs is a `GAME_TYPE_GENERATORS` name-keyed registry in `github-wizard.js`, not an inline branch. Every generated app's own `package.json` declares its composed-site route (`bloobitygook.route`, see `scripts/compose-site.mjs` under Deployment) — an app-identity value baked at generation time same as port/id, just like every other app's `package.json` does. `repo-edits.js` patches the *fetched* current content of root `package.json` (just the new `dev:<id>` script — the `build` script discovers `apps/*` dynamically and needs no per-app edit); it no longer touches `scripts/compose-site.mjs` at all, since that script now discovers routes itself. `github-wizard.js` orchestrates branch → write files (passing the one patched file's fetched `sha`, which GitHub's contents API requires for updating an existing file, not just creating one) → PR via an injected Octokit-shaped client (so the whole flow is unit tested without ever touching the real repo). Auth is a user-supplied fine-grained GitHub PAT stored only in `localStorage`. The generated PR body's one remaining manual checklist item is running `pnpm install` and committing the updated `pnpm-lock.yaml` — the wizard can't run pnpm from a browser, so a new app's dependencies never make it into the lockfile on its own; CI wiring itself is fully automatic (see Deployment below). Multi-scene-per-game configuration and in-editor menu building are explicitly not built yet — deferred, not designed around.

None of `publish.js`/`games.js`/`github-wizard.js`/`scaffold/*`/`ui-helpers.js` needed structural changes for the dashboard restructure — they never touched the DOM or routing, so their tests kept passing verbatim (`games.js` only grew new exports, didn't change existing ones). Good confirmation that pulling pure logic out of DOM-wiring early (a pattern started with `ui-helpers.js` back when the editor was still vanilla JS) keeps paying off as the app grows.

## Deployment

One Firebase project, two Hosting sites: `play` (target name, despite the name it now serves the *composed* `dist-site/` — hub at `/`, tetris/pacman/blob at their sub-paths) and `editor` (its own separate site). `scripts/compose-site.mjs` copies each game app's `dist/` into `dist-site/<route>/` after they're all built; the route mapping is no longer a hand-maintained list in this script — it reads each `apps/*` directory's own `package.json`'s `bloobitygook.route` field (`""` means the site root; a missing field, as on `apps/editor`, means "not part of the composed site"), so a new game app needs zero edits here as long as its own `package.json` declares a route (the wizard's generated `package.json` already does — see `apps/editor`'s scaffold/wizard bullet above). Root `package.json`'s `build` script (`pnpm --filter "./apps/*" -r run build && pnpm compose`) discovers every `apps/*` workspace package dynamically too, so adding a game app is genuinely a zero-central-edit operation end to end.

Storage (`storage.rules`): `scenes/`, `archetypes/`, `games/`, and `drafts/games/` are all public read except `drafts/games/` (`canEdit`-only read too, since it's working data `apps/hub` never touches). Writes are two-tier, both still just email allowlists (no custom claims — deliberately, for a small roster): `canEdit` can write `scenes/`, `archetypes/`, and `drafts/games/` (archetypes are shared building blocks, same tier as scenes — not a "publish this game" gate); only the smaller `canPublish` can write `games/`, since that path is what publishing a game actually means. `apps/editor/src/permissions.js`'s `canPublish` list is a UI-only duplicate of the rules' allowlist, kept in sync by hand. `firebase deploy --only storage` after editing that file — it's not automatic (the `archetypes/` block added alongside the archetype system hasn't been deployed yet as of this writing — `apps/editor`'s Archetypes UI will 403 on list/save until it is).

**`functions/` (Phase 7)**: one Storage-triggered, 2nd-gen Cloud Function, `rebuildGamesIndex` in `functions/index.js` — on any write to `games/<id>/manifest.json`, re-reads every manifest under `games/` and writes an aggregated `games/index.json` that `apps/hub` fetches directly. Eventarc-backed (no manual Pub/Sub setup); runs under the Admin SDK, so it bypasses `storage.rules` entirely rather than needing its own write exception. Outside the pnpm workspace (`pnpm-workspace.yaml` only globs `apps/*`/`packages/*`) — Firebase manages `functions/`'s own `npm install` independently. Requires the Blaze plan and Eventarc/Cloud Functions APIs enabled before `firebase deploy --only functions` will succeed (one-time manual setup, not automated by CI); `games/index.json` needs one manifest re-save through the editor's "Manage Games" panel after first deploy to bootstrap it. The pure aggregation logic (`functions/buildIndex.js`, `functions/manifestPath.js`) is unit tested; the Admin SDK wiring itself needs the Storage emulator (which needs a local Java install) to test directly, so treat it as unverified beyond code review until confirmed against a real deploy.

`.github/workflows/ci.yml` (test + build every app on PR/push, plus — since Phase 7 — a Firebase Hosting preview-channel deploy of `play`/`editor` on same-repo pull requests, giving a real hosted URL to test a new/changed game before merge) and `deploy.yml` (same build, plus `firebase deploy` with `channelId: live` on push to `main` — required there since only `pull_request` context lets the action infer live-vs-preview automatically).

## Coordinate systems

Per-app, not shared: blob demo is `800×600`; Tetris is `240×480` at 24px cells (10×20 board); Pac-Man is `352×288` at 32px cells (11×9 board); `apps/goop` and `apps/scene-player` are `800×600`, same as the blob demo (and the fixed canvas `apps/editor`'s Stage authors scenes against — `apps/scene-player` reuses the same bounds so a scene plays back exactly as authored). All SVG, y grows downward.

## Testing philosophy

Pure logic lives apart from DOM-wiring wherever the two can be separated (`ui-helpers.js` in the editor, `movement.js`/`maze.js`/`ghostAI.js` in Pac-Man, `collision.js`/`cellGroup.js` in grid) — that's what makes most of this unit-testable without jsdom or a real browser at all. Where wiring correctness genuinely matters (collision resolution, movement algorithms, trigger integration), live-browser verification supplements the unit tests: driving the actual built modules with constructed scenarios via the dev tools, not just trusting that passing unit tests imply correct end-to-end behavior. This caught at least one real bug (Pac-Man's movement rounding) that a narrower single-call unit test wouldn't have.

## Known gaps

- Stage-building landed platforms, moving platforms, and configurable goals (`packages/platformer`'s `platformCarrySystem`, `packages/behavior`'s `patrolKinematic`, a `"goal"`-category archetype + `packages/triggers` zone entry, all playable via `apps/scene-player`) — still missing: one-way platforms, hazards/damage, ladders.
- `storage.rules`' new `archetypes/` block hasn't been deployed yet (`firebase deploy --only storage` still pending as of this writing) — the editor's Archetypes UI will 403 on list/save until it is.
- Archetype inheritance (`extends`/`resolveArchetype`) is a working, tested data model with no authoring UI yet — creating a `extends` relationship means hand-editing the archetype's JSON (or publishing it via a script), not picking a parent in `ArchetypeEditor.jsx`.
- Scene navigation is a single-`nextSceneId` chain, not a graph — no branching, no level-select menu. A game's scenes are only discoverable by following the chain from its entry `sceneId`; there's no index of "every scene this game has."
- `packages/engine/src/hierarchy.js`'s parent-child relationship (`attachChild`/`hierarchySystem`) is wired into both `apps/editor` and `apps/scene-player`'s render loops, but nothing authors a real parent-child relationship yet — no archetype/scene format exposes "attach this to that," so it's validated by unit test only, same status `seekToward`/`fleeFrom` had before `apps/goop`.
- `platformCarrySystem` only handles a rider standing on top of a platform — not being pushed from the side, not standing on a slope. Every other collision in `packages/engine` is circle-vs-circle/circle-vs-bounds; a real rect-collision pass would be needed for either of those, and isn't planned.
- `packages/behavior`-driven animation switching (e.g. a `walk` animation while moving, `idle` at rest) isn't wired up — only one named animation exists per character/archetype so far, nothing to switch between yet; archetypes with an `svg` visual can't animate at all this pass (see `packages/objects`' `archetype.js`).
- No platformer wizard game-type yet — `apps/goop` was hand-built, matching how Tetris was hand-built before its stage-assembly rewrite got a wizard template.
- "Script-programmed" behavior is presets only (`stationary`/`patrol`/`chase`) — no visual rule-builder, no user-authored code (deliberately, to avoid an arbitrary-code-execution surface).
- Input-driven behavior only supports typed keys so far (no gamepad/pointer), per the explicit initial scope.
- `packages/behavior`'s `seekToward`/`fleeFrom` aren't used by any app yet (see above) — validated by unit test only.
- No drag-to-move for placed objects in the editor canvas; position only changes via spawn point or loaded scene data. No undo anywhere.
- Not tested on touch/mobile input.
- Nothing is published to the hub by default — a human has to sign in (with `canPublish` permission specifically) and use the editor's dashboard/`GameMetadataForm` (or, soon, an actual finished game from the wizard) to get an entry listed.
- `apps/editor`'s production bundle is over Vite's 500kB warning threshold (React + Firebase + Octokit) — acceptable for a dev-only tool, not worth code-splitting yet.
- `apps/fertris` is still the wizard's blank scaffold (`createWorld`+`startLoop`, no game logic) plus a local editor scene (`apps/editor/public/scenes/fertris.json`) enabling its 7 Tetris piece types + the spawner tool for authoring. Placing pieces/spawners in the editor and saving them into a scene is now possible (see `packages/objects` above), but nothing reads a placed spawner to actually drive falling-piece gameplay yet — that's deliberately deferred to a follow-up pass, once the authoring side has been used for real.
